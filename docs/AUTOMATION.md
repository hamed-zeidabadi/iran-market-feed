# بروزرسانی خودکار هر ۱۰ دقیقه

workflow اصلی روی شاخهٔ پیش‌فرض `main` با رویداد `schedule` در دقیقه‌های ۷، ۱۷، ۲۷، ۳۷، ۴۷ و ۵۷ UTC اجرا می‌شود. نیازی به push یا روشن‌بودن سیستم محلی نیست؛ push و اجرای دستی هم برای تغییر کد و بازیابی سریع باقی مانده‌اند. فاصلهٔ برنامه‌ریزی‌شده در JSON و Schema برابر ۶۰۰ ثانیه است.

در بررسی ۱۴۰۵/۰۸/۲۰، workflow قبلی فعال و شاخهٔ پیش‌فرض صحیح بود. فقط دو اجرای `schedule` در سابقه ثبت شده بود: `2026-11-10T18:48:12Z` و `2026-11-10T23:58:35Z`؛ هر دو collect و deploy موفق بودند. بنابراین برنامه فقط با push اجرا نمی‌شد، اما زمان‌بندی نیم‌ساعتهٔ مورد انتظار به‌صورت منظم تحویل نشده بود. برای زمان‌های فاقد run، لاگ collector یا خطای سورس وجود ندارد؛ علت قطعی حذف آن رویدادها از اطلاعات مخزن قابل اثبات نیست.

[مستندات GitHub](https://docs.github.com/en/actions/reference/workflows-and-actions/events-that-trigger-workflows#schedule) تأخیر یا حذف رویدادهای schedule در بار زیاد را صریحاً بیان می‌کند. [گزارش وضعیت GitHub](https://www.githubstatus.com/api/v2/incidents.json) نیز اختلال Actions در بخشی از ۱۰ نوامبر را ثبت کرده است؛ این گزارش به‌تنهایی تمام فاصله‌های خالی این مخزن را توضیح نمی‌دهد.

cron جدید خارج از ابتدای ساعت است. سقف collect شش دقیقه و deploy سه دقیقه شد تا اجرای معلق برای مدتی طولانی مانع نوبت‌های بعد نشود. هر اجرا همان فایل `public/api/prices.json` را بازنویسی و در Pages منتشر می‌کند؛ commit خودکار قیمت یا تاریخچه نداریم.

GitHub cron تضمین اجرای دقیق در ثانیهٔ مقرر ندارد. مصرف‌کننده باید `datetime` خروجی را برای زمان واقعی تولید و `published_at` اقلام را برای زمان اعلام قیمت بخواند. در نبود نرخ تازه، `null` و وضعیت واقعی منتشر می‌شود؛ تغییر ساعت تولید، قیمت دیروز را تازه نمی‌کند.

## وضعیت اندازه‌گیری‌شده (۱۴۰۵/۰۸/۲۰)

- تا 07:20Z پس از تغییر cron به هر ۱۰ دقیقه (05:49Z) هیچ run با `event=schedule` ثبت نشد؛ چند نوبت cron گذشته بود.
- دو run قدیمی schedule در `18:48:12Z` و `23:58:35Z` ساخته شده‌اند، یعنی دقیقه‌ای غیر از ۷ و ۳۷ که cron آن زمان تعریف می‌کرد. علت قطعی مشخص نیست.
- [مستندات GitHub](https://docs.github.com/en/actions/reference/workflows-and-actions/events-that-trigger-workflows#schedule) تأخیر یا حذف را مجاز می‌داند، حداقل فاصله را ۵ دقیقه اعلام می‌کند و اجرای schedule را فقط روی شاخهٔ پیش‌فرض می‌پذیرد. در مخزن عمومی پس از ۶۰ روز بی‌فعالیتی غیرفعال می‌شود؛ این مخزن در این بازه نیست.
- بنابراین `schedule` GitHub برای هدف «هر ۱۰ دقیقه» تضمین ندارد و علت نبود run روشن نشده است.

## scheduler خارجی (آماده، نیازمند credential)

پوشهٔ `scheduler/cloudflare` یک Cloudflare Worker با cron ‏`3-59/10 * * * *` است. Worker فقط `workflow_dispatch` همین workflow را روی `main` صدا می‌زند؛ قیمت ذخیره یا منتشر نمی‌کند و endpoint عمومی ندارد. اگر run در صف باشد dispatch جدید نمی‌زند و خود workflow با `concurrency` اجرا و انتشار را پشت‌سرهم نگه می‌دارد.

راه‌اندازی (یک بار):

1. حساب Cloudflare (طرح رایگان کافی است) و `npx wrangler login`.
2. ساخت fine-grained PAT فقط برای همین مخزن با دسترسی `Actions: Read and write`.
3. در پوشهٔ `scheduler/cloudflare`: `npx wrangler secret put GITHUB_TOKEN` و سپس `npx wrangler deploy`.

توکن نباید در سورس، URL یا چت قرار بگیرد. cron داخلی GitHub به‌عنوان مسیر اضافی باقی می‌ماند؛ اجرای هم‌زمان دو مسیر فقط باعث انتشار پشت‌سرهم همان فایل می‌شود.
